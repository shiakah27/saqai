# المعمارية والقرارات الهندسية

## المكونات ومسؤولياتها

| المكون | مسؤول عن | ممنوع عليه |
|---|---|---|
| ESP32 #1 (عقدة الحساسات) | BME280 + لوحة المطر MH-RD + 3 حساسات تربة. إطار قراءات كل 2 ث، Debounce للمطر، حدث مطر فوري | أي قرار ري |
| ESP32 #2 (عقدة التشغيل) | **قرار الري** (`saqai_decision.h`)، اختيار المنطقة الأحوج، تشغيل صمام واحد + المضخة، حدود السلامة المحلية، تقرير القرار والتشغيل | تجاوز قفل المطر |
| Backend `readingsService` + `liveService` | استقبال الإطار، بثه مباشرة للوحة (SSE)، تخزين مخفف (طقس كل 60 ث، تربة كل 10 ث) | القرار |
| Backend `actuatorService` | تجهيز مدخلات القرار لعقدة التشغيل كل ثانية، تسجيل قراراتها وعملياتها، رفض بدء التشغيل وقت القفل | اختيار المنطقة أو المدة |
| `safetyService` + `rainLockout` | قفل المطر، إلغاء الأوامر اليدوية، فترة الانتظار بعد المطر | التنبؤ |
| AI service (FastAPI) | Features من قراءات المحطة → احتمال المطر خلال 3 ساعات + تفسير | الأوامر والحالة والعتاد |
| `scheduler` | تنبؤ كل 30 د، انتهاء الانتظار، صلاحية الأوامر اليدوية، تشغيلات متأخرة → FAILED، حالة الأجهزة | قرار ري |
| PostgreSQL | المصدر الوحيد للحقيقة، وسجل كامل لكل قرار وتشغيل وحدث | — |
| Dashboard | العرض، وأوامر الصيانة بمفتاح الإدارة فقط | اتخاذ قرار ري |

## لماذا القرار على ESP32 #2؟

- **يعمل حيث تُنفذ المياه**: اللوحة التي تفتح الصمام هي التي تقرر، بأحدث قراءة (عمرها ≤ ثانية)، بلا انتظار دورة على الخادم.
- **القواعد نفسها مختبرة على اللابتوب**: `saqai_decision.h` بلا أي اعتماد على Arduino، فيُترجم بـg++ ويُختبر 28 اختبارًا، ويستخدمه اختبار e2e عبر `decide_cli`.
- **الخادم يبقى صاحب الأمان**: القرار على اللوحة، لكن قفل المطر والرفض والسجل على الخادم. لو قررت اللوحة الري أثناء القفل، يرفض الخادم بدء التشغيل قبل فتح الصمام.

## سلّم القرار (لكل منطقة، كل ثانية)

```
1 SAFETY    مطر الآن / RAIN_LOCKOUT / COOLDOWN / ERROR / حساسات قديمة   → HOLD   (لا يُستشار التنبؤ أصلًا)
2 SENSOR    لا قراءة / قراءة غير صالحة                                → SKIP
3 NEED      التربة ≥ الهدف                                             → SKIP AT_TARGET
4 SOAK      رُويت قبل أقل من soak_s (التسرب)                            → SKIP
5 PULSES    وصلت حد النبضات (3) → قفل 30 د                             → SKIP
6 DAILY     تجاوزت الحد اليومي                                         → SKIP
7 CRITICAL  تحت الحد الحرج                                             → IRRIGATE (الأعلى أولوية، يتجاهل التنبؤ)
8 FORECAST  p ≥ threshold (مع Hysteresis)                              → DEFER (حتى 3 ساعات، بعدها ري مخفّض)
9 BELOW_TARGET / CLOSED_LOOP_PULSE                                     → IRRIGATE (نبضة تكميلية ≤ 10 ث)
```

المدة = العجز × seconds_per_percent، تُزاد في الحر الشديد وتُخفض في الرطوبة العالية، بين 3 و60 ثانية.
ثم `chooseZone()`: من بين مناطق IRRIGATE، الأعلى **Urgency** (العجز نسبةً لهدف المنطقة، والجافة حرجًا فوق الجميع) هي الوحيدة التي تُروى. البقية "ينتظر دوره".

## Data flow

```
ESP32 #1 ── كل 2 ث ── POST /api/readings {طقس + مطر + تربة×3}
   → live frame في الذاكرة → SSE للوحة فورًا
   → weather_readings (كل 60 ث) · soil_readings (كل 10 ث)
scheduler كل 30 د → آخر 4 ساعات من weather_readings → AI /predict → rain_predictions

ESP32 #2 ── كل 1 ث ── GET /api/actuator/inputs
   ← {system_mode, rain_lockout, sensors_fresh, rain_detected, weather, prediction, zones[], engine, active_run_id, manual}
   → decide() لكل منطقة → chooseZone()
   → POST /api/actuator/decisions (عند التغير أو كل 30 ث) → irrigation_decisions (مع trace)
   → POST /api/actuator/run {event: started}   ← يرفضه الخادم وقت القفل → لا ماء
   → كل الصمامات OFF → صمام المنطقة → 300 ms → المضخة
   → يراقب كل ثانية: مطر، قفل، حساسات قديمة، إلغاء، وصول الهدف، 60 ث
   → المضخة OFF → الصمام CLOSED → POST /api/actuator/run {event: finished}
```

## Emergency rain flow

```
لوحة المطر: 3 قراءات مبللة متتالية (≈3 ث، قراءة كل ثانية)
  → ESP32 #1: POST /api/rain-event RAIN_STARTED فورًا (يعيد كل 1 ث حتى 201)
  → Backend، معاملة واحدة مع قفل system_state:
       mode = RAIN_LOCKOUT · إلغاء الأوامر اليدوية · تأكيد التأجيلات الصحيحة · الأحداث · بث للوحة
  → ESP32 #2 في استعلامه التالي (≤ 1 ث): rain_lockout = true
       → Pump OFF → Valve CLOSED → finished cancelled/RAIN_OVERRIDE
جاف 5 دقائق متصلة → RAIN_STOPPED → COOLDOWN (RAIN_COOLDOWN_MINUTES) → NORMAL
  → عقدة التشغيل تعود للقرار بقراءات التربة الحية
```

كل إطار قراءات فيه `rain_detected=true` يفعّل القفل أيضًا، لو ضاع الحدث.

## Fail-safe

| ماذا لو… | ما يحدث |
|---|---|
| انقطع Wi-Fi أو توقف الـBackend أثناء الري | ESP32 #2 يوقف بعد 3 استعلامات فاشلة (≈3 ث) `BACKEND_UNREACHABLE`، ولا يبدأ ريًا جديدًا |
| توقفت عقدة الحساسات | `sensors_fresh=false` بعد 10 ث → HOLD لكل المناطق، وإيقاف أي تشغيل `SENSORS_STALE` |
| سلك AO للوحة المطر مفصول | المقاومة 100kΩ تسحب AO إلى 0 = "مبلل" → قفل المطر حتى يُصلح (الخيار الآمن) |
| BME280 فشل أو قراءة مستحيلة | لا يُرسل إطار → الحساسات قديمة → لا ري |
| حساس تربة مفصول أو قيمة مستحيلة | `valid=false` → `SENSOR_INVALID` لتلك المنطقة فقط |
| توقفت خدمة الذكاء | `AI_UNAVAILABLE` → القرار على التربة وحدها (`NO_FORECAST`) |
| بداية التشغيل (< 3 ساعات تاريخ) | `INSUFFICIENT_HISTORY` → التربة وحدها، وقسم الجاهزية يعرض التقدم |
| تنبؤ قديم | يُتجاهل إذا تجاوز 2.5 × فترة التنبؤ |
| مطر أثناء التشغيل | الإيقاف خلال ثانية |
| الخادم ألغى التشغيل (تشغيل آخر، إعادة ضبط) | `active_run_id` لا يطابق → `COMMAND_REVOKED` |
| المضخة لا تتوقف أو الجهاز صامت | حد محلي 60 ث في ESP32 + الخادم يعلّم التشغيل المتأخر FAILED |
| أبلغ الجهاز عن عطل | النظام ERROR حتى تلغيه الإدارة |
| أمر يدوي قديم | `command_id` + `expires_at` (60 ث)، ويُلغى عند المطر |
| انقطاع كهرباء ESP32 #2 | NO contacts: المضخة والصمامات تُفصل تلقائيًا |

## لماذا هذه التقنيات

- **HTTP + Polling كل ثانية بدل MQTT:** زمن الإيقاف عند المطر ≤ ثانية، وهذا يكفي للري. MQTT يضيف Broker ونقطة فشل.
- **SSE للوحة:** القراءات تصل اللوحة لحظيًا بلا WebSocket ولا مكتبات.
- **تخزين مخفف:** الحساسات لحظية، لكن قاعدة البيانات تحفظ صفًا للطقس كل دقيقة وللتربة كل 10 ث، فلا تتضخم.
- **FastAPI منفصل للذكاء:** فشله لا يُسقط الـBackend ولا يوقف الري.
- **SQL مباشر بلا ORM**، و**React + Vite** تُبنى ويقدمها نفس الـBackend.
- **Random Forest، أفق 3 ساعات:** أفضل PR-AUC من 5 نماذج. ساعة لا تكفي لتأجيل مفيد، و6 ساعات تؤجل كثيرًا في حر الرياض.
